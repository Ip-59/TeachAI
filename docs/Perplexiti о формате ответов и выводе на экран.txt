## Как я понимаю задачу

Вы хотите, чтобы нейроучитель по API возвращал учебный материал, который фронтенд может сразу красиво отрисовать:

- заголовки, абзацы, списки;
- Python-код с сохранением отступов и подсветкой синтаксиса;
- при необходимости изображения, графики или ссылки на них;
- без «мусорных» символов, двойного форматирования и ручной очистки ответа.

И главный вопрос: **насколько современные API-модели, включая GPT от OpenAI, надежно соблюдают заданный формат — JSON или Markdown — и какой формат лучше требовать?**

## Короткий ответ

Современные модели стали значительно надежнее, но правильный подход изменился: **не просить модель «сделай красивый Markdown» и не парсить свободный текст, а требовать строго типизированный JSON через Structured Outputs**. Внутри JSON-полей можно хранить Markdown для учебного текста и отдельные блоки для кода.

OpenAI прямо разделяет два режима: обычный JSON mode гарантирует лишь синтаксическую валидность JSON, а **Structured Outputs с `strict: true` гарантирует соответствие ответа вашей JSON-схеме** — при условии, что схема использует поддерживаемое подмножество JSON Schema. [developers.openai](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)

## JSON vs Markdown

| Формат | Насколько надежен | Для чего подходит | Риск |
|---|---|---|---|
| Свободный Markdown | Средне: модель обычно умеет писать Markdown, но нет машинной гарантии структуры | Черновой текст, чат, простая демонстрация | Лишние блоки, непоследовательные заголовки, код не всегда выделен корректно |
| JSON mode | Высокая валидность JSON, но **нет гарантии нужных полей и структуры** | Простые случаи, когда достаточно «какого-нибудь» JSON | Модель может вернуть не те ключи или вложенность  [help.openai](https://help.openai.com/en/articles/8555517) |
| JSON Schema / Structured Outputs | Максимальная: структура соответствует схеме при `strict: true` | Продуктовый нейроучитель, UI, БД, тесты | Нужно правильно спроектировать схему; поддерживается не весь JSON Schema  [developers.openai](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses) |

То есть требование «ответь Markdown» модель обычно выполнит reasonably well, но это **соглашение на уровне промпта**, а не формальная гарантия API. Для вашего случая это именно та категория надежности, которая раньше приводила к сбоям.

## Что рекомендую для нейроучителя

Лучший практический шаблон — **JSON-конверт + Markdown внутри полей**:

- JSON нужен интерфейсу как надежный контракт: какие блоки есть, в каком порядке, какого они типа.
- Markdown нужен внутри текстовых блоков: он удобен для заголовков, списков, формул, выделений и вставки кода.
- Python-код лучше класть в отдельное поле или отдельный блок, а не «прятать» его внутри обычного абзаца.

Пример схемы ответа:

```json
{
  "lesson": {
    "title": "Циклы в Python",
    "summary": "Краткое объяснение темы.",
    "blocks": [
      {
        "type": "text",
        "markdown": "Цикл `for` позволяет перебирать элементы последовательности."
      },
      {
        "type": "code",
        "language": "python",
        "code": "for i in range(3):\n    print(i)"
      },
      {
        "type": "image",
        "alt": "Схема работы цикла for",
        "url": "https://example.com/for-loop.png"
      },
      {
        "type": "quiz",
        "question": "Что выведет этот код?",
        "options": ["0 1 2", "1 2 3"],
        "correct_index": 0
      }
    ]
  }
}
```

Здесь интерфейс не должен «угадывать», где код, а где текст: он читает `type` и вызывает соответствующий компонент — Markdown-рендерер, code viewer с подсветкой, image viewer или quiz widget.

## Как это реализовать с OpenAI

В Chat Completions API задается `response_format` с `type: "json_schema"`, `strict: true` и вашей схемой; API reference отмечает, что такой режим обеспечивает соответствие ответа заданной схеме.  OpenAI рекомендует использовать Structured Outputs вместо обычного JSON mode, когда это поддерживается. [developers.openai](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)

Важно: `strict: true` гарантирует **структуру**, но не гарантирует, что Markdown внутри поля будет идеальным по стилистике. Поэтому в системном промпте стоит отдельно зафиксировать правила:

- «В поле `markdown` используй только Markdown; не оборачивай весь ответ в ```markdown```»;
- «Python-код размещай только в блоках `type: "code"`»;
- «Не добавляй полей вне схемы»;
- «Не используй HTML, если он не разрешен схемой».

И все равно валидируйте ответ через Pydantic / `jsonschema` на сервере: это дешевая страховка и удобный способ дать понятную ошибку или повторить запрос.

## Почему не стоит полностью отказываться от обработки

Вашу прежнюю идею «получил ответ — сразу вывел» можно почти реализовать, но не через regex-фильтры, а через **структурный рендеринг**:

1. LLM возвращает строгий JSON.
2. Сервер валидирует JSON по схеме.
3. Фронтенд итерирует `blocks`.
4. Для `text` используете проверенный Markdown-рендерер.
5. Для `code` используете компонент с подсветкой Python и `white-space: pre` / `pre-wrap`, чтобы отступы не потерялись.
6. Для `image`, `quiz`, `formula` и т. п. используете отдельные компоненты.

Так вы убираете главную причину старых сбоев: formerly вы пытались восстановить структуру из неструктурированного текста; теперь модель отдает структуру явно.

## Практический вывод

- **Для отображения ученику:** Markdown внутри JSON — удобный и правильный выбор.
- **Для надежности API-интеграции:** требуйте JSON Schema со `strict: true`, а не «просто JSON» или «просто Markdown».
- **Для кода:** отдельный блок `code` с явным `language: "python"` — это надежнее, чем код внутри Markdown-строки.
- **Для OpenAI GPT:** используйте Structured Outputs; это именно механизм, созданный для вашей исходной проблемы — детерминированной структуры ответа. [openai](https://openai.com/index/introducing-structured-outputs-in-the-api/)
- **Для локальных моделей через Ollama:** если строгий JSON Schema-режим недоступен или работает нестабильно, используйте JSON mode плюс Pydantic-валидацию и одну автоматическую повторную попытку с сообщением об ошибке валидации.

Иными словами: ваша прежняя архитектура «LLM → грязный текст → фильтр → UI» была принципиально уязвимой. Современная архитектура — «LLM → строгий JSON → валидация → компонентный рендерер» — решает именно эту проблему.
