## 1. Краткое резюме

**TeachAI** — прикладная образовательная система на Python, работающая в **Jupyter Notebook**. Она использует **готовую большую языковую модель (LLM)** через API и создаёт персонализированные учебные материалы: план курса, содержание уроков, практические примеры, тестовые вопросы, ответы на вопросы студента, контрольные задания по коду.

Система **не обучает** и **не дообучает** свою нейросеть, **не собирает** обучающий датасет, **не использует** RAG и **не выполняет** парсинг для подготовки выборки. Эти этапы дипломного трека **согласованы с куратором**.

Технический вклад диплома:

- модульная архитектура и интерактивный UI в Jupyter;
- **многошаговые** вызовы LLM с разными промптами;
- инженерия качества (валидация, фильтрация, перегенерация, постобработка кода);
- сохранение прогресса обучения;
- **экспериментальное обоснование выбора модели** (сравнение 5 LLM, 13.09.2026).

Этап №5 (финальная версия системы + экспериментальный ноутбук) **принят куратором**. Базовая модель в системе: **`gpt-4o-mini`**. Документированный апгрейд по качеству: **`gpt-5.6-luna`**.

## 3. Постановка задачи

### 3.1. Проблема

Создание качественного **персонализированного** учебного курса вручную трудоёмко: структура, тексты, примеры, проверка. Типовой курс плохо учитывает темп (часы, длительность занятия) и стиль объяснений.

Нужна **прикладная система**, которая ведёт обучение через **уже обученную** LLM, а не разрабатывает собственную модель с нуля.

### 3.2. Решение

**TeachAI** оркестрирует цепочку обращений к LLM и прикладную логику: профиль → план курса → уроки → материалы по запросу → проверка знаний → прогресс. Пользователь работает через **ipywidgets** в Jupyter.

---

## 4. Цель и задачи

### 4.1. Цель

Разработать систему **TeachAI** для **автоматической генерации персонализированного учебного контента** на **предобученной LLM через API**, без датасета и без fine-tuning, с прохождением курса в Jupyter, сохранением прогресса и **обоснованным выбором модели**.

### 4.2. Задачи (реализовано)

1. **Генерация контента** — план, уроки, примеры, тесты, Q&A, контрольные задания.
2. **Персонализация** — имя, объём курса в часах, длительность занятия, стиль (formal / friendly / casual / brief).
3. **Интерактивность** — сценарий в Jupyter: настройка, курс, урок, примеры, вопрос, тест, практика.
4. **Контроль качества LLM** — валидация плана, примеров, релевантности вопроса; проверка кода контрольных.
5. **Учёт прогресса** — локальный JSON: профиль, план, кэш уроков, оценки, контрольные.
6. **Экспериментальный выбор модели** — сравнение готовых LLM на типовых промптах урока (этап №5).

## 5. Что проект намеренно не делает (согласовано)

| Этап / подход | Статус для TeachAI |
|---------------|-------------------|
| Сбор обучающей базы для обучения НС | Не применяется, этап пройден с пояснением |
| Парсинг для датасета | Не применяется |
| Обучение / fine-tuning своей модели | Не применяется |
| RAG (векторная БЗ + чанки + поиск) | Не применяется |
| Классические CV-задачи | Не относится к проекту |

**Как объяснять:** проект — **inference-система** на знаниях предобученной GPT. Качество: промпты, структура ответа, программная валидация и **сравнение готовых моделей**, а не обучение весов.

Аналог терминов этапа 5: «точность / параметры» → **балл судей / цена / latency**; «history обучения» → графики бенчмарка, не эпохи.

## 6. Архитектура (логическая)

### 6.1. Оркестратор

При запуске инициализируется **движок**, который подключает:

- конфигурацию (ключ API, режим подключения, имя модели);
- состояние (JSON на диске);
- фасад генерации контента (все учебные запросы к LLM);
- оценивание (тесты);
- UI (настройка, урок, тест, завершение);
- дашборд при повторном входе (ленивая тяжёлая инициализация по кнопке);
- системный лог.

### 6.6. Вопрос ученика: от запроса до ответа

Это штатный путь экрана урока (кнопка «Задать вопрос»). Другие кнопки (примеры, тест, контрольное) идут своими генераторами и на этой схеме не смешиваются.

1. Ученик вводит вопрос в виджете урока и отправляет его.
2. Система увеличивает счётчик вопросов этого урока и сохраняет его в `state.json`.
3. Фасад генерации передаёт вопрос в проверку релевантности вместе с текстом урока. Предпочтительно сырой текст урока, не оформленный HTML. Из текста срезается «шапка» курса, раздела и темы, чтобы модель не судила вопрос по названию курса.
4. Проверка идёт ступенями: сначала локальные правила по тексту, затем эвристика по метаданным урока. Если они не дали однозначного ответа — отдельный запрос к LLM. Ответ проверки — структура: относится ли вопрос к уроку, уверенность, причина, подсказки.
5. Если вопрос **не** по уроку, на экран выводится предупреждение с причиной. Ответ по существу **не** запрашивается.
6. Если вопрос по уроку, отдельный генератор ответов собирает свой промпт: курс, раздел, тема, урок, текст урока, имя ученика, стиль общения. Это **второй** вызов LLM, не продолжение проверки.
7. Текст ответа показывается в том же виджете. Поле ввода очищается.

```
Ученик
  |
  |  текст вопроса
  v
Экран урока (поле вопроса)
  |
  +--> Счётчик вопросов --> state.json
  |
  v
Фасад генерации
  |
  v
Проверка релевантности
  |  очистка текста урока, срез шапки
  |  локальные правила / эвристика
  |  при необходимости ----> LLM (JSON: по теме или нет)
  |
  +-- не по теме --> предупреждение на экране (стоп)
  |
  +-- по теме --> Генератор ответа
                      |
                      |  свой промпт: урок + стиль + вопрос
                      v
                    LLM (текст ответа)
                      |
                      v
                    Ответ в виджете
```

Счётчик вопросов в этом пути только записывается. Напоминание «вы задали больше трёх вопросов» в коде есть, но текущий экран урока его **не показывает**. На защите это не заявлять как работающую функцию.

### 6.7. Полный путь: от профиля до оценки

Это весь сценарий обучения, не только вопрос. Скриншоты реальной сессии лежат в `doc/` (файлы `.png`). Цифры на них (часы, проценты, «5 из 8 уроков») — **пример одной сессии**, не норматив системы и не метрика качества генерации.

1. Ученик открывает ноутбук и выполняет одну стартовую ячейку. Создаётся движок.
2. При первом входе форма профиля: имя, общее время курса в часах, длительность урока в минутах, стиль общения. Профиль пишется в `state.json`.
3. Ученик выбирает курс из каталога (пять направлений). Описание курса берётся из каталога, не из LLM.
4. Отдельный запрос к LLM строит план: разделы, темы, уроки, в формате JSON. Структура проверяется программно и сохраняется в состояние.
5. Открытие урока: если текст уже в кэше, повторного запроса нет. Иначе LLM пишет урок с учётом стиля и имени. На экран идёт оформленный HTML, для проверки вопросов хранится сырой текст.
6. Дальше ученик сам выбирает действия. Примеры, объяснение, понятия, вопрос, тест и контрольное — **разные** запросы со своими промптами.
7. Вопрос идёт по цепочке раздела 6.6: сначала проверка темы, затем ответ.
8. Тест: LLM составляет вопросы с вариантами, система сравнивает выбор ученика с эталонным индексом. Тест пройден при оценке **больше 40%**.
9. Контрольное: ученик пишет код, запускает его, система проверяет результат. Урок считается завершённым, если тест пройден **и** контрольное принято, либо урок отмечен вручную.
10. Повторный запуск показывает дашборд: курс, прогресс, текущий урок. Полная инициализация — по кнопке «Продолжить обучение».

```
Профиль -> выбор курса -> план (LLM, JSON)
    -> урок (кэш или LLM)
        -> примеры / объяснение / понятия
        -> вопрос: проверка темы -> ответ
        -> тест (порог > 40%)
        -> контрольное (код ученика)
    -> прогресс в state.json -> дашборд
```

## 7. Работа с языковой моделью

### 7.1. Модель и API

- Режим: **inference** через Chat Completions (клиент OpenAI / совместимый шлюз).
- Модель задаётся переменной **`LLM_MODEL`** в `.env`.
- **В дипломе:** `LLM_MODEL=gpt-4o-mini` — вердикт этапа №5, не произвольный выбор.
- Все учебные генераторы используют **одну** эту модель; меняются **параметры** запроса (`temperature`, `max_tokens`, JSON-формат).
- Для части проверки контрольных заданий может задаваться отдельная **`VALIDATION_MODEL`** (иначе та же `LLM_MODEL`).
- Повторы запроса при сбоях сети (retry) есть в базовом клиенте.

**История:** раньше модель была жёстко `gpt-3.5-turbo-16k`; модуль `llm.py` удалён. Смена модели — через `.env`.

**Подключение:** по умолчанию **прямое** (`OPENAI_CONNECTION_MODE=direct`); HTTP-прокси — только если явно включён режим `proxy`. Не утверждать на защите, что «прокси обязателен».

### 7.2. Многошаговая логика

Система **не** сводится к одному запросу «сгенерируй курс». Отдельные промпты:

| Тип контента | Назначение |
|--------------|------------|
| План курса | JSON: разделы → темы → уроки |
| Урок | Текст теории под стиль общения |
| Примеры | Код и пояснения |
| Тест | Вопросы с вариантами |
| Q&A | Ответ по уроку |
| Понятия / объяснение | Углубление |
| Релевантность вопроса | JSON: относится ли вопрос к уроку |
| Контрольное задание | Условие, стартовый код, эталон |

Это закрывает критерий **multi-step** для LLM-проектов. Production-форма в дипломе — **Jupyter + ipywidgets** (не веб-сервис).

### 7.3. Персонализация

В промпты идут стиль общения, имя, контекст курса. Для Python-уроков — жёсткое требование: примеры кода на **Python**.

## 8. Обеспечение качества (без 95/90/85)

Формальной ML-accuracy на hold-out **нет**. Есть инженерные механизмы и отдельный **бенчмарк моделей** (раздел 9).

### 8.1. План курса

JSON от LLM + программная проверка и автокоррекция структуры.

### 8.2. Примеры (по кнопке пользователя)

Формат `{title, description, code}`. Цепочка: генерация → валидация (минимум примеров, Python, запрет HTML/JS) → синтаксис (`ast`) → при необходимости правка типичных шаблонов LLM и перегенерация.

### 8.3. Вопрос студента

Многоступенчато: очистка HTML урока, срез «шапки» курса, эвристики по базовому Python, при необходимости LLM с **текстом урока** (не только заголовком). Нерелевантный вопрос отклоняется с подсказкой.

В кэше урока хранятся HTML для показа и **сырой текст** для анализа.

### 8.4. Контрольные и тест

Контрольное: генерация задания, выполнение кода студента, типизированная проверка и/или LLM-валидация.  
Тест: вопросы от LLM, сравнение с эталонным индексом варианта. Порог прохождения теста: **оценка > 40%**. Урок считается завершённым, если тест пройден **и** контрольное верно, либо урок отмечен принудительно.

### 8.5. Кэш и устойчивость

Урок кэшируется в состоянии и переиспользуется. API-клиент повторяет запросы при сбоях.

## 9. Эксперимент выбора модели (этап №5)

Это **не** таблица версий промптов. Это сравнение **готовых LLM** на одном и том же промпте урока TeachAI.

### 9.1. Зачем

Выбор `gpt-4o-mini` изначально был практическим. Для сдачи LLM-проекта нужно **экспериментальное обоснование**. Классическое обучение своей сети в архитектуре отсутствует — вместо эпох сравнивались модели.

### 9.2. Протокол (13.09.2026)

| Параметр | Значение |
|----------|----------|
| Объект | Генерация **текста урока** (критический сценарий TI) |
| Курс | Основы Python, стиль `friendly` |
| Темы | 5 уроков: переменные, условия, циклы, списки/словари, функции |
| Участники | `gpt-4o-mini`, `gpt-5.6-luna`, `gpt-5.6-terra`, `claude-5-sonnet`, `gemini-3.5-flash` |
| Судьи | `gpt-5.6-sol`, `claude-opus-5`, `gemini-3.1-pro` (три семейства, слепые метки A–E) |
| Форма | Автофильтр: объём, markdown-заголовки, блок Python-кода. **25/25** прошли |
| Смысл | Рубрика 0–2: тема, полнота, плотность, педагогика, соответствие заданию; сумма **0–10** |
| Шлюз эксперимента | GPTunnel (цены в ₽ на дату прогона) |

**Оговорка протокола:** судьям уроки обрезали до ~3500 символов с начала (иначе JSON судей ломался на длинных ответах). Ядро оценки (`topic_fit`, педагогика, плотность) считали надёжным; хвост урока (`task_fit` / заключение) — с оговоркой. Полные тексты и цена/latency считались **без** обрезки.

Оценён только тип «урок», не весь конвейер TI (план, Q&A, примеры — в спецификации как следующие шаги).

### 9.3. Результаты полного прогона

| Место | Модель | Балл (0–10) | ₽/урок | Балл/₽ | Latency |
|------:|--------|------------:|-------:|-------:|--------:|
| 1 | gpt-5.6-luna | **8.40** | 0.88 | 9.57 | ~84 с |
| 2 | gemini-3.5-flash | 8.33 | 6.53 | 1.28 | ~21 с |
| 3 | gpt-5.6-terra | 8.27 | 8.78 | 0.94 | ~82 с |
| 4 | **gpt-4o-mini** | 7.73 | **0.53** | **14.72** | **~12 с** |
| 5 | claude-5-sonnet | 7.67 | 7.57 | 1.01 | ~37 с |

Стоимость полного эксперимента ≈ **322 ₽** (генерации + судьи).

Дымовой прогон на 1 уроке дал другую картину (лидер Claude). Вывод: **одного урока недостаточно**.

### 9.4. Вердикт (зафиксирован до интерпретации приоритетами)

Приоритеты учебного проекта: (1) балл на рубль, (2) приемлемое качество, (3) низкая цена и latency, (4) прохождение format gate.

**Базовую модель `gpt-4o-mini` оставляем.** Это не «лучшая модель вообще», а лучший **рабочий** вариант для учебного TI.

**Апгрейд при бюджете:** `gpt-5.6-luna` (лидер качества при цене всё ещё ~1 ₽/урок).

**Не берём для массовых уроков:** Terra, Claude Sonnet 5, Gemini 3.5 Flash — дорого относительно прироста качества.

Воспроизведение: сохранённый JSON + ноутбук `Model_Benchmark.ipynb` (живой прогон опционален).

## 12. Почему без fine-tuning и своего датасета

1. Цель диплома — **система обучения**, не тренировка весов.
2. Промпты + валидация + сравнение готовых моделей покрывают задачу.
3. Нет объёма данных и бюджета на осмысленный fine-tuning.
4. Универсальность: разные темы курса без переобучения.
5. Согласовано с куратором на этапах 2–3; этап 5 принят в той же логике.

## 13. Ограничения (честно)

- Бенчмарк покрывает **уроки**, не все роли LLM в системе.
- Обрезка текстов для судей влияет на `task_fit` длинных ответов.
- LLM-as-judge ≠ живой методист; зато протокол воспроизводим.
- Цены — тарифы шлюза на дату прогона.
- Нет A/B-журнала версий промптов.
- Зависимость от внешнего API (доступность, стоимость).
- Полностью устранить ошибки LLM нельзя.

## 16. Глоссарий
