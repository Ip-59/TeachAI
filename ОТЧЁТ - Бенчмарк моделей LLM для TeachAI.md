## 1. Цель и постановка задачи

### 1.1. Зачем понадобился отдельный этап

В основном проекте TeachAI для генерации учебных материалов используется API OpenAI. Базовая модель — **`gpt-4o-mini`**, для части задач валидации предусматривалась более сильная модель семейства GPT-4o. Этот выбор был сделан **прагматически** (доступность, цена, привычный API), а не по результатам сравнительного эксперимента на типовых промптах TeachAI.

На рынке одновременно доступны модели других провайдеров (Anthropic Claude, Google Gemini и др.) и более новые линейки OpenAI (семейство GPT-5.x). Поэтому потребовалось:

1. проверить, насколько текущий выбор хорош **именно для сценариев учителя TI**;
2. сравнить качество ответов на **одних и тех же** промптах;
3. учесть не только «красоту текста», но и **стоимость** и **скорость**;
4. сделать вывод: оставить `gpt-4o-mini`, заменить на другую модель или разделить роли (дешёвая / умная).

### 1.2. Что сознательно не делалось

- Не создавался полный дубль интерфейса TeachAI.
- Не проводилось fine-tuning и не собиралась обучающая база.
- Не оценивались все типы генераций сразу (план курса JSON, Q&A, контрольные) — в первом полном прогоне фокус на **генерации текста урока** как главной «критической» генерации.
- Человек не выставлял баллы по каждому тексту вручную: критерии и рубрика заданы заранее, оценку по смыслу выполняли **модели-судьи** (LLM-as-judge).

### 1.3. Принципиальная методология

Эксперимент строился так, чтобы минимизировать предвзятость «доказать, что ChatGPT хорош»:

| Принцип | Как реализовано |
|---------|-----------------|
| Одинаковые условия | Один и тот же промпт урока для всех участников (логика как в `LessonGenerator`) |
| Критерии до прогона | Рубрика зафиксирована в `model_benchmark/rubric.json` |
| Слепая оценка | Судьям тексты подавались как «Урок A/B/C/D/E» без имён моделей |
| Несколько судей из разных семейств | OpenAI + Anthropic + Google — чтобы снизить «любим своих» |
| Два слоя оценки | Автопроверка формы + смысловые баллы судей + стоимость/latency |
| Честный вывод | Допускается рекомендация сменить базовую модель |

```

├── format_gate.py          # автопроверка формы ответа

├── runner.py               # оркестрация: генерация → gate → судьи → сводка

└── results/                # JSON-отчёты прогонов
Model_Benchmark.ipynb       # ноутбук отчёта / запуска
```

### 2.2. Шлюз GPTunnel

Вместо OpenRouter выбран **GPTunnel**:

- единый доступ к моделям разных провайдеров;
- формат запросов совместим с OpenAI Chat Completions;
- `base_url`: `https://gptunnel.ru/v1`;
- авторизация: заголовок `Authorization` с ключом **без** префикса `Bearer`;
- для тестового личного счёта: параметр `useWalletBalance=true`;
- в ответе `usage` есть не только токены, но и **`total_cost` в рублях** — это позволило сразу включить стоимостную оценку.

Идентификаторы моделей сверены живым запросом `GET /v1/models` по ключу проекта.

## 3. Объект эксперимента: задания (сценарии)

### 3.1. Почему именно генерация урока

В TeachAI нейросеть выполняет несколько ролей (план курса, урок, примеры, Q&A, понятия, контрольные). Для первого сравнительного этапа выбрана **критическая генерация** — текст урока:

- это основной объём контента, который видит студент;
- промпт длинный и жёсткий (структура, markdown, код Python, без HTML, без прощаний);
- по нему хорошо видно и качество педагогики, и умение следовать инструкции.

Остальные типы сценариев (`course_plan`, `qa`, `examples`) описаны в `SPEC.md` как следующие шаги бенчмарка.

### 3.2. Курс и параметры промпта

| Параметр | Значение |
|----------|----------|
| Курс | Основы Python |
| Раздел | Основы языка |
| Стиль общения | `friendly` |
| Имя пользователя в промпте | Студент |
| Temperature генерации | 0.7 |
| max_tokens генерации | 3500 |
| System / user промпт | по образцу `LessonGenerator` TeachAI |

Промпт требовал: введение; концепции; примеры; практика; частые ошибки; краткое заключение без прощаний; код только в блоках ` ```python `; markdown, не HTML.

### 3.3. Список заданий (5 уроков)

| ID | Тема | Название урока |
|----|------|----------------|
| `lesson-variables` | Переменные и типы данных | Переменные, числа и строки |
| `lesson-conditions` | Условные операторы | if, elif, else на практике |
| `lesson-loops` | Циклы | Циклы for и while |
| `lesson-lists-dicts` | Списки и словари | Работа со списками и словарями |
| `lesson-functions` | Функции | Создание и вызов функций |

Итого на полном прогоне:

- **5 уроков × 5 участников = 25 генераций**;
- **5 уроков × 3 судьи = 15 судейских оценок** (каждая оценка содержит баллы по всем 5 участникам);
- **15 × 5 = 75 частных оценок** (модель × урок × судья), сводимых в средние.

## 5. Судьи (LLM-as-judge)

### 5.1. Кто оценивал

Выбраны **старшие** модели трёх разных семейств:

| ID | Модель | Семейство |
|----|--------|-----------|
| `judge-gpt-5.6-sol` | `gpt-5.6-sol` | OpenAI |
| `judge-claude-opus-5` | `claude-opus-5` | Anthropic |
| `judge-gemini-3.1-pro` | `gemini-3.1-pro` | Google |

### 5.2. Почему именно так

- Один судья мог бы систематически завышать «своих»; три судьи из разных вендоров сглаживают эффект.
- Temperature судейства: **0.2** (меньше случайности, чем у генерации).
- max_tokens судьи: **4000**.
- Ответ судьи — только JSON по схеме рубрики; при битом JSON — одна повторная попытка исправить формат.

### 5.3. Обрезка текста урока для судьи (принятое решение протокола)

#### Решение

В целях сокращения объёма текста, передаваемого судье, **было принято решение обрезать каждый урок до ~3500 символов** (с начала текста). Полные ответы участников при этом сохранялись в JSON результатов и учитывались при расчёте цены и latency без обрезки.

#### Зачем это сделали

При передаче судье сразу пяти полных длинных уроков (особенно 11–14 тыс. символов у Luna/Terra) ответ судьи (JSON с баллами) получался слишком большим/нестабильным: парсер ломался, прогон обрывался. Обрезка — мера, чтобы судейский контур стабильно завершался.

#### Что судья видел и что не видел

Типовая структура урока TeachAI:

1. введение  
2. основные концепции и определения  
3. подробные объяснения с примерами  
4. пошаговые инструкции / алгоритмы  
5. практические применения  
6. частые ошибки  
7. заключение  

**В лимит ~3500 символов обычно попадало основное содержание:**

- введение;  
- ключевые концепции и определения;  
- начало / существенная часть объяснений и примеров кода.

**За счёт обрезки у длинных ответов судья чаще не доходил до следующих частей (они оставались в «хвосте»):**

- продолжение развёрнутых примеров и дополнительных подразделов;  
- практические применения «в реальной жизни»;  
- блок **«частые ошибки»**;  
- **заключение / краткая сводка**.

Точная граница зависит от модели и темы: у коротких ответов (`gpt-4o-mini`, иногда Gemini) урок целиком укладывался в 3500 символов, и обрезки фактически не было. У длинных (Luna, Terra, часто Claude) в хвост уходили именно поздние разделы.

#### Аргументация: оценка основного содержания не пострадала

Обрезка **не отменяла** оценку главного педагогического ядра урока. Судья по видимой части полноценно оценивал:

- `topic_fit` — соответствие теме;  
- `pedagogy` — понятность объяснений и примеров;  
- `density` — насыщенность видимого материала (не «вода» в начале).

Именно эти критерии отражают **основное содержание** урока (чему учат и как объясняют), а не только наличие финальных служебных блоков промпта.

Ограничение протокола сильнее влияет на:

- `task_fit` (видел ли судья полный набор разделов задания, включая «ошибки» и «заключение»);  
- частично на `completeness`, если полноту судили по наличию финала.

Поэтому в интерпретации результатов:

- сравнения по **педагогике и теме** считаем достаточно надёжными;  
- сравнения по **формальной полноте структуры до конца** — с оговоркой (короткие ответы здесь получают преимущество видимости, а не обязательно качества ядра).

Это **ограничение протокола оценки**, а не автоматический дефект длинной модели.

## 6. Рубрика и слои оценки

### 6.1. Format gate (автомат, до судей)

| Проверка | Порог |
|----------|-------|
| Минимальная длина | ≥ 800 символов |
| Markdown-заголовки | обязательны |
| Блок кода Python | обязателен ` ```python ` |

Результат полного прогона: **все 25 генераций прошли format gate** (провалов формы не было).

### 6.2. Смысловая рубрика (судьи)

Шкала по каждому критерию: **0 / 1 / 2**.

| ID | Критерий | 0 | 1 | 2 |
|----|----------|---|---|---|
| `topic_fit` | Соответствие теме | мимо | частично | чётко по теме |
| `completeness` | Полнота | обрывок | основное есть | достаточно для изучения |
| `density` | Объём и плотность | пусто/вода | терпимо | насыщенно без воды |
| `pedagogy` | Педагогичность | плохо | средне | понятно новичку |
| `task_fit` | Соответствие заданию | нет структуры | частично | структура/код/ошибки/заключение |

**Total за урок от одного судьи** = сумма пяти критериев (**0…10**).

Итоговый балл модели = среднее `total` по всем урокам и всем судьям (**n = 15** на участника).

### 6.3. Стоимость и скорость

Из `usage` GPTunnel:

- `avg_gen_cost_rub` — средняя цена **одной генерации урока** участником;
- `sum_gen_cost_rub` — сумма по всем урокам участника;
- `avg_latency_sec` — среднее время ответа;
- `score_per_ruble` = `avg_total / avg_gen_cost_rub` (выше = выгоднее по качеству на рубль);
- отдельно: `sum_judge_cost_rub` — цена работы судей (**накладные эксперимента**, не цена продакшена TI).

## 7. Ход работ (хронология этапа)

1. **Постановка:** отдельный тестер, не клон TI; сравнение на типовых промптах; критерии до прогона.
2. **Уточнение оценки урока:** форма — фильтр; смысл — судьи по рубрике; человек задаёт правила.
3. **Фиксация SPEC:** курс Python, 5 тем, участники, судьи, GPTunnel.
4. **Актуализация моделей:** вместо устаревшего акцента на GPT-4o взяты GPT-5.6 / Claude 5 / Gemini 3.x из живого каталога GPTunnel.
5. **Реализация модуля** `model_benchmark/` + ноутбук.
6. **Дымовой прогон** (1 урок `lesson-variables`) — проверка пайплайна.
7. **Первый полный прогон** — прерван ошибкой GPTunnel `502 Bad Gateway`.
8. **Ретраи в клиенте** (502/503/429) и **успешный полный прогон** всех 5 уроков.
9. **Включение стоимости** в leaderboard (не «потом», а в том же отчёте).

- **Sol** относительно высоко оценил mini (часто хвалил полноту структуры короткого ответа).

Разногласие судей — ожидаемо; итоговый рейтинг поэтому строится по **среднему трёх**, а не по одному вердикту.

## 9. Интерпретация для TeachAI

### 9.1. Достаточно ли текущий `gpt-4o-mini`?

**Да, как рабочий baseline — достаточно**, если приоритет:

- минимальная цена (~0.53 ₽/урок в этом прогоне);
- минимальная latency (~12 с);
- приемлемое качество (~7.7/10) и высокая полнота формальной структуры.

Но он **не лучший по качеству**: отстаёт от Luna примерно на 0.7 балла при том, что Luna всё ещё дёшева (~0.88 ₽).

### 9.2. Лучший компромисс качество / цена

**GPT-5.6 Luna** — главный кандидат на смену/дополнение базовой модели:

- 1-е место по качеству (8.40);
- цена того же порядка, что mini (около 1 ₽ за урок, не 7–9 ₽);
- высокий `score_per_ruble` среди «сильных» ответов.

### 9.3. Что не выглядит оптимальным для массовой генерации уроков

| Модель | Почему |
|--------|--------|
| GPT-5.6 Terra | Качество почти как у Luna, цена ~**в 10 раз** выше |
| Claude Sonnet 5 | Дорого; средний балл ниже Luna/Gemini; риск «воды» и огрехов в коде |
| Gemini 3.5 Flash | Хорошее качество и скорость, но ~7× дороже Luna при близком балле |

### 9.4. Определяющие критерии решения

Перед вердиктом зафиксированы **приоритеты** для генерации уроков TeachAI (в порядке важности) с учётом того, что проект **учебный**:

1. **Экономическая эффективность** (`score_per_ruble` = средний балл / средняя цена урока) — максимум полезного качества на рубль.
2. **Приемлемое абсолютное качество** (`avg_total`) — не «провал», а рабочий уровень для демо и обучения.
3. **Низкая стоимость массовой генерации** и **низкая latency** — уроков много, бюджет и ожидание ответа ограничены.
4. **Пригодность для конвейера TI** (format gate, структура задания).

**Не** определяющими признаны: погоня за максимальным баллом любой ценой; смена стека «ради новизны»; результат одного дымового урока.

По этим критериям:

| Модель | Балл | Цена/урок | Балл/₽ | Вывод |
|--------|-----:|----------:|-------:|--------|
| **gpt-4o-mini** | 7.73 | **0.53 ₽** | **14.72** | лучшая отдача на рубль |
| gpt-5.6-luna | **8.40** | 0.88 ₽ | 9.57 | лучшее качество при умеренной доплате |
| Gemini / Terra / Claude | ~7.7–8.3 | 6.5–8.8 ₽ | ~0.9–1.3 | для массовых уроков невыгодны |

### 9.5. РЕШЕНИЕ (вердикт этапа)

**Принимаем решение: базовую модель генерации уроков `gpt-4o-mini` оставляем без изменений.**

Это **наименее затратное** обоснованное решение для учебного проекта: модель уже в TI, даёт приемлемое качество, лидирует по баллу на рубль и по скорости.

| Вопрос | Ответ |
|--------|--------|
| Меняем default сейчас? | **Нет** |
| Почему оставляем mini? | Лучший `score_per_ruble` (14.72); минимальная цена и latency; качество достаточное (~7.7/10), не «провал» |
| Оговорка | Решение осознанно **экономическое**, а не «mini — лучшая модель вообще» |
| Если нужна выше качество и есть бюджет | Рекомендуется переход на **`gpt-5.6-luna`** (лидер по абсолютному баллу 8.40 при цене всё ещё ~1 ₽/урок) |
| Что не предлагаем для уроков | Terra, Claude Sonnet 5, Gemini 3.5 Flash — дорого относительно прироста качества |

**Логика одной фразой:** для учебного TeachAI оставляем **самый выгодный рабочий вариант** (`gpt-4o-mini`); **Luna** — рекомендуемый апгрейд «заплатить чуть больше → получить заметно лучше», а не обязательная замена.

## 10. Ограничения эксперимента (честно)

1. Оценён только тип генерации **«урок»**, не весь TI.
2. Для судьи длинные уроки обрезались до ~3500 символов с начала: в хвост часто уходили продолжение примеров, практика, «частые ошибки», заключение. Оценка основного содержания (`topic_fit`, `pedagogy`, `density`) сохранялась; сильнее затрагивались `task_fit` / полнота финала.
3. LLM-as-judge ≠ идеальный методист-человек; зато воспроизводим и масштабируем.
4. Цены — тарифы GPTunnel на дату прогона; у другого шлюза цифры могут отличаться.
5. Stochasticity LLM: при другом seed/температуре ранжирование может чуть сдвинуться; поэтому важны **5 тем × 3 судьи**, а не один запрос.
6. Первый полный запуск упал на 502 — инфраструктура агрегатора тоже фактор риска для продакшена.
